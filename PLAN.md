## 3. Decision log

Decisions made with user input, kept here so the reasoning doesn't get lost as the code changes:

- **Scope shape for the original build:** a fully working demo on synthetic data, not a compressed pilot — real data access, licensing, and RMF paperwork have external lead times no amount of solo effort shortens. (Section 4.1)
- **Stack for the original build:** code-native (Python + DuckDB + Streamlit + Plotly), not Power BI — Power BI needs a tenant/workspace/license before anything can be shown, which the original 24-hour window couldn't absorb. (Section 4.1)
- **Power BI integration method:** export-based (Parquet + DAX mapping), not a live DAX/XMLA connection — simpler, doesn't require Power BI Pro/Premium yet, and upgrades cleanly later if warranted. (Section 4.2)
- **The conversational layer stays custom permanently**, even once Power BI is available for dashboards — handing it to Power BI's own Copilot/Q&A would lose the explainability/scope-safety behavior already built and tested. (Section 4.2)
- **Measure definitions are bilingual by construction** (SQL + DAX in one registry, `MEASURE_DOCS`), with the Power BI-facing doc generated from that registry rather than hand-written, specifically so the two can't silently drift apart. (Section 4.2)
- **LLM provider: OpenRouter**, chosen by the user rather than defaulting to a hosted Anthropic/OpenAI key. **Model: `nvidia/nemotron-3-ultra-550b-a55b:free` originally, switched to `google/gemma-4-31b-it:free` in round 7** for speed and rate-limiting reasons — both verified to exist and support tool-calling via OpenRouter's public model list before committing to them, and both re-tested against the full question suite after switching rather than assumed equivalent. (Sections 4.6, 4.7)
- **On LLM failure or rate-limit: fall back to the keyword matcher, silently from the user's perspective but transparently labeled** ("Interpreted by: 🤖 LLM" vs. "🔤 keyword matcher (fallback)") — chosen over surfacing a hard error, so a rate-limited free model doesn't make the feature unusable. (Section 4.6)
- **API key storage: local `.env` file, gitignored**, over requiring a shell environment variable each session — convenience over the marginal extra security of not persisting it to disk. (Section 4.6)
- **An LLM's explicit "no match" gets a second opinion from the keyword matcher, but that opinion is only trusted if it comes with a caveat.** Originally treated as fully authoritative; revised with user input after finding a real case (Section 4.6 / QUESTION_TEST_LOG.md round 6) where that produced a less helpful bare rejection instead of a caveated partial answer the keyword matcher could have given. A *caveated* keyword match after an LLM "no" is now surfaced as the answer (labeled `keyword_after_llm_no_match` so the disagreement is visible); a *clean, uncaveated* keyword match in the same situation is still discarded, since that combination is more likely the keyword matcher's own false positive than a genuine LLM miss.
- **Multi-user auth: build real working login/roles, not just document the design.** Chosen with user input over a documentation-only approach, specifically so "audit logging of who asked what" (a gap GOVERNANCE_NOTES.md already named) would become a true statement, not an aspirational one. (Section 4.8)
- **RMF categorization: document both as-built (Low, synthetic data) and target (Moderate, real CUI data) explicitly, rather than picking one.** Chosen with user input so the package doesn't overstate current risk or understate real-deployment risk. (Section 4.8)
- **RMF package scope: the full battery** (categorization, SSP, SAP, SAR, POA&M), not just the core SSP/POA&M pair — chosen with user input, accepting that the SAP/SAR are necessarily more speculative (no real assessor or real system to assess yet) in exchange for a more complete starting package. (Section 4.8)

### 4.1 Original 24-hour sprint

**Reality check on scope compression:** the original 24-week plan included things that cannot compress to 24 hours regardless of effort — real SQL database access requests, Power BI tenant/licensing setup, an actual pilot user group, and RMF/ATO paperwork all have external lead times (approvals, other people's calendars) that no amount of solo effort shortens. Rather than pretend those fit, the plan changed *shape*: build a fully working, self-contained, demoable prototype on synthetic post-mission data that proves every required capability end-to-end in code. It's a proof-of-concept artifact, not a piloted system — that was the honest tradeoff for the timebox.

**Stack swap from the original 24-week plan, and why:** Power BI was dropped in favor of a code-native stack (Python + DuckDB + Streamlit + Plotly) for the initial build. Power BI needs a tenant, workspace, and license seat before anything can be built or shown — setup friction the 24-hour window couldn't absorb. The code stack runs locally, immediately, and is inspectable line-by-line, which also made the "explainable/verifiable" requirement easier to demonstrate honestly in a short build.

**LLM layer note:** no LLM API key was (or is) available in this environment. The conversational layer was built as a real architectural component (question → structured intent → SQL against the semantic layer → chart), but the "understand the question" step uses a template/pattern-matching stand-in instead of a live LLM call. This was called out explicitly, not hidden — and the code isolates it behind one function (`interpret_question()`) so swapping in a real LLM API call later is a one-function change, not a rebuild.

Proved: an end-to-end pipeline from messy raw data → cleaned → governed semantic layer → visualization, working and inspectable; a working conversational-query architecture (question → query → chart → explanation → manual-verify path), even with a template stand-in instead of a live LLM; what good measure documentation and a visible cleansing/governance log look like in practice; multiple visualization types including geospatial.

### 4.2 Power BI swap path

Once the initial build was working end-to-end, the next priority was making the dashboard layer easy to hand off to Power BI later without a rewrite, since Power BI is a plausible production BI tool for this org and a real workspace is expected to become available.

Decisions and reasoning are in the Decision Log (Section 3). Mechanically: `warehouse/export_for_powerbi.py` exports the cleaned fact/dimension tables (not pre-aggregated views — Power BI's modeling strengths are the fact/dimension pattern) to Parquet; `warehouse/semantic_layer.py::MEASURE_DOCS` carries a DAX formula alongside every measure's SQL; `warehouse/generate_powerbi_measures_doc.py` renders those into [POWERBI_MEASURES.md](POWERBI_MEASURES.md) so the two can't drift; [POWERBI_MIGRATION.md](POWERBI_MIGRATION.md) is the click-by-click path from export to a working Power BI report. None of this has been run against a real Power BI instance yet (see Open Items).

### 4.3 Conversational-layer safety hardening (six rounds)

Prompted by the round-1 finding that a confident-but-wrong-scope answer is more dangerous than an honest "I don't understand" (because a rendered chart gives a user no reason to doubt it).

- **Round 1 (test):** ran 15 realistic questions, found 2 that silently answered the wrong scope while claiming success (a community-comparison question and a readiness-trend question against a measure with no time dimension).
- **Round 2 (fix):** added a caveat mechanism that detects those two specific unsupported-dimension patterns and surfaces them as prominent warnings instead of silently dropping the unhandled part of the question; also fixed two real gaps found along the way (equipment-specific entity filtering, superlative-aware sorting). Eliminated the "wrong but confident" category entirely (0/15).
- **Round 3 (close remaining gaps + a live-caught regression):** implemented "last N months" time-windowing and order-independent phrase matching for a previously-missed rephrasing. Live-testing the time-window fix in the running app (not the automated test list) caught a *new* regression — the entity-matching fallback logic matched the digit in "last 3 months" against a unit name ending in "3," silently mis-scoping the answer. Fixed by requiring a second, non-trivial word from the unit name to also match.
- **Round 4 (a second data source finds two more real bugs):** adding the training-currency data source and intent (Section 4.4) surfaced the same failure shape again, in a new form — a training question about time trends got silently answered with an unrelated mission-count chart because the generic "trend" intent was checked before the new domain-specific one. Fixed by always checking domain-specific intents before the generic one. A second bug (a sort-direction error on "most expired") was also found and fixed.
- **Round 5 (a third data source + proactive adversarial probing):** adding the maintenance data source (Section 4.5) went smoothly on its own six test questions, so testing deliberately went further — adversarial probes designed to break the matcher, not just realistic questions. Found a wrong-domain answer from a plain substring collision ("ready" inside "already," unrelated to any entity name) and fixed it with word-boundary matching everywhere keywords are checked; that fix immediately broke a previously-passing question ("trends" no longer matched by singular "trend" once boundaries were enforced), caught by re-running the full suite and fixed by allowing an optional plural "s". A second sort-direction bug ("most unresolved" needing ascending, not descending, sort) was also found and fixed, mirroring round 4's "most expired."

- **Round 6 (the LLM swap itself):** see Section 4.6 — real API testing found a crash-class bug (an LLM-attached entity with no matching column in its chosen view), a prompt-completeness bug (intents needed plain-language descriptions, not just IDs, for the model to map vocabulary correctly), and a genuine unresolved design tradeoff (an LLM's authoritative "no" can be less helpful than the keyword matcher's caveated partial answer for the same known gap).

Score progression across rounds on the growing question set: 6/15 → 8/15 → 10/15 → 13/19 → 15/25 fully correct through round 5 (keyword matcher only); round 6 introduces a second interpreter and a new failure class (crashes) that required its own fix rather than a score to chase. Full per-question detail and the cross-round pattern (every round that added surface area found a genuine bug of the same shape) are in [QUESTION_TEST_LOG.md](QUESTION_TEST_LOG.md).

### 4.4 Second data source: training/certification records

Added to demonstrate the "heterogeneous data sources" requirement concretely rather than asserting it from a single dataset. `data/generate_synthetic_data.py` now also generates `training_records.json` — a JSON export (not CSV) simulating a separate training-management system, with its own messiness profile (mixed ISO/US date formats, orphan person references, invalid validity periods). `pipeline/clean.py` ingests it through the same logged-cleansing discipline as every other source. The resulting `v_training_currency_by_unit`/`v_training_currency_by_certification` measures are the first in the semantic layer built on a two-hop relationship (training_records → personnel → units, rather than a direct unit_id link), and required updating `warehouse/export_for_powerbi.py` and [POWERBI_MIGRATION.md](POWERBI_MIGRATION.md) to describe that multi-hop relationship for Power BI. See Section 4.3 for the NL-layer bugs this addition surfaced.

### 4.5 Third data source: maintenance/discrepancy events (SQLite)

Added specifically to make the "connect to SQL databases" part of the requirement concrete — the first two sources are flat files (CSV, JSON); this one is generated straight into a real SQLite database (`data/raw/maintenance.db`) and `pipeline/clean.py::clean_maintenance_events` ingests it via an actual `sqlite3` connection and `pd.read_sql` query, not a file parse. Its messiness is a different *kind* than the other sources': the `resolved` field is stored under several inconsistent text encodings (`"1"/"0"`, `"Y"/"N"`, `"true"/"false"`), realistic for a SQL table with no enforced boolean type across data-entry eras, and normalized to a single boolean during cleansing. `equipment_type` deliberately reuses the *same* vocabulary as the readiness source — a conformed dimension across two independently-generated sources, so a real "downtime vs. readiness by equipment type" comparison is actually answerable. Two measures resulted: average downtime by equipment type, and discrepancy resolution rate by unit — the first pair in the registry where the two dimensions are genuinely different measures, not just different groupings of one, which required generalizing the NL layer's chart-spec Y-column and adding a per-intent entity-to-dimension override (see `app/nl_query.py`'s "maintenance" intent). See Section 4.3 (round 5) for the NL-layer bugs this addition's testing surfaced.

### 4.6 The LLM swap: OpenRouter + nvidia/nemotron-3-ultra-550b-a55b:free

Every round of Section 4.3 hardened a keyword-matching stand-in while `app/nl_query.py`'s docstring kept describing where a real LLM would plug in. This section is that swap actually happening, at the user's request and with a user-supplied OpenRouter API key.

**What was built:** `app/llm_interpret.py` calls the model via OpenRouter's OpenAI-compatible `/chat/completions` endpoint, using tool-calling (`tool_choice` forced to a single function) to constrain the response to a structured `{intent_id, dimension, entity_type, entity_value}` shape — the model is given the known entity vocabulary (unit names, mission types, equipment types, certifications) explicitly in the system prompt and instructed never to invent values outside it. `interpret_question()` in `app/nl_query.py` tries this path first when `OPENROUTER_API_KEY` is configured, and falls back to the keyword matcher (Section 4.3) on any technical failure (network error, timeout, malformed response, rate limit) — but treats an explicit LLM "no match" as authoritative, not a failure, so the keyword matcher doesn't get to override a decision the model actually reasoned about.

**Key design choices** (see Decision Log): OpenRouter + the specific free Nemotron model, per explicit user instruction (verified to exist and support tool-calling via OpenRouter's public model list before committing engineering effort to it); fallback-on-failure rather than surfacing an error, so a rate-limited free tier doesn't make the feature unusable; API key in a gitignored `.env` file rather than a shell-only environment variable, for convenience; LLM `no_match` treated as authoritative.

**What testing against the real API found** (full detail in QUESTION_TEST_LOG.md round 6): a crash-class bug where the LLM attached a valid-vocabulary entity to an intent whose chosen view had no matching column at all (fixed with an explicit `valid_entity_columns` check on every intent, run centrally before any entity_filter reaches SQL — a stronger safeguard than the wrong-scope caveats from earlier rounds, since this prevented an unhandled crash, not just a wrong answer); a prompt-completeness gap where the model couldn't map real vocabulary ("unresolved discrepancies") to the right intent because the prompt gave it only IDs and dimension names, not descriptions (fixed by adding an `llm_description` to every intent); and real, observed rate-limiting on the free model mid-test-run, which the fallback design handled exactly as intended — every affected question fell through to the keyword matcher automatically and answered no worse than it would have before the LLM existed.

One tradeoff was found where the LLM's authoritative "no" was less helpful than the keyword matcher's caveated partial answer for the same known, already-documented gap (readiness has no time dimension). Since this was a product judgment call rather than a bug with one correct fix, it was resolved by asking the user rather than deciding unilaterally: the keyword matcher now gets a second opinion after any LLM `no_match`, but that opinion is only trusted when it comes back with a caveat of its own (see the Decision Log entry above and QUESTION_TEST_LOG.md round 6's follow-up section for the reasoning and the deterministic tests that verified all three branches of the resulting logic).

### 4.7 Model swap: Nemotron → Gemma, and the failure class that reopened

The Nemotron model from Section 4.6 was heavily rate-limited on its free tier and slow (a reasoning-by-default model, sometimes 20-40+ seconds per call). At the user's request, swapped to `google/gemma-4-31b-it:free` — checked against OpenRouter's public model list for existence and tool-calling support first, same as the original model choice.

**On the axes the swap was made for, it was a clear win:** average LLM latency dropped to ~1.8s (from Nemotron's multi-second-to-40-second range), and rate-limiting during a full 25-question test run kicked in noticeably later.

**It also reopened a failure class rounds 1-5 existed to close, through a different model's own bias rather than a bug in this codebase's logic:** Gemma showed a much stronger tendency than Nemotron to classify time-related phrasing as the generic "trend" intent regardless of actual domain — "readiness trend by month" and "training currency trends by month" were both answered with the unrelated mission-count chart and **no caveat at all**, a silent wrong-domain answer. **Fix:** rather than patching the prompt for this one model's quirk, added a standing, model-agnostic cross-check: whenever ANY interpreter (LLM or keyword) lands on "trend," the keyword matcher's own domain-priority logic (which already exists to prefer domain-specific intents over generic "trend," see Section 4.3 round 4) re-validates that choice. A different domain intent, if the keyword matcher would pick one, wins instead — letting the existing time_trend-mismatch caveat fire automatically. This protects against the *next* model's version of this same bias too, not just Gemma's.

**A second, genuinely new caveat category was also found:** "Which unit has the most missions overall?" got answered with the trend view's raw per-month line chart — correct domain, but a chart type that structurally cannot answer a ranking question (a line chart shows per-month values, not a single ranked total). Nemotron had rejected this question outright; Gemma answered it confidently. **Fix:** a new caveat fires when the trend intent is chosen with no entity filter (comparing across units) and the question contains ranking language ("most," "highest," etc.), naming the mismatch explicitly rather than presenting a chart that doesn't actually settle what was asked.

Full detail, including the deterministic test results confirming no regressions on the existing bar-chart-based ranking questions (which have real ranking support and are correctly unaffected), in QUESTION_TEST_LOG.md round 7. **The standing lesson across seven rounds now spans two different axes of change** — new data/intent surface area, and a different model behind the same interpreter interface — both requiring the same full-suite-plus-live-verification discipline, neither exempted by "it's still just an LLM call."

### 4.8 Multi-user auth and the RMF package

Both explicitly out of scope for the original 24-hour prototype ("not useful to build against a synthetic single-user prototype" per the earlier decision log) — taken on at the user's request once the rest of the build had matured.

**Auth (`auth/`):** real login and session state (`auth/auth.py::require_login`), two roles seeded by `auth/seed_users.py` (admin, analyst) with bcrypt-hashed password storage, and role-based page visibility in `app/main.py` — an analyst can use the dashboards and conversational layer but cannot see the governance panel or the audit log. Every conversational query is now logged (`auth.log_query()`) with username, role, timestamp, question, interpreter, and caveat count, closing the audit-logging gap `GOVERNANCE_NOTES.md` had named as missing since round 1. Verified live: wrong-password rejection, successful login for both roles, role-gated page visibility, sign-out, and an audit-log entry actually appearing after a query — not just unit-tested in isolation.

**RMF package (`rmf/`):** a full five-document set —
- [SYSTEM_CATEGORIZATION.md](../rmf/SYSTEM_CATEGORIZATION.md): FIPS 199 categorization, documented as both as-built (Low, synthetic data) and target (Moderate, real CUI data), per the user's explicit choice not to conflate the two.
- [SSP.md](../rmf/SSP.md): control-by-control status against a representative NIST SP 800-53 Rev 5 Moderate-baseline subset, every "Implemented"/"Partial" status pointing at the actual responsible code (e.g., IA-5 → `auth/seed_users.py`'s bcrypt hashing; SI-10 → `app/nl_query.py`'s parameterized queries), not asserted without a reference.
- [SAP.md](../rmf/SAP.md) / [SAR.md](../rmf/SAR.md): an assessment plan written so an independent assessor could execute it directly, plus a preliminary self-assessment report against it — explicitly labeled as NOT an independent assessment, since the same team that built the system also wrote these findings.
- [POAM.md](../rmf/POAM.md): every open gap as a POA&M line item (owner/date fields deliberately left as `TBD`, since no real program exists to assign them), plus an explicit "path to an actual ATO" section stating plainly that an ATO is an Authorizing Official's risk-acceptance decision, not something a development session — or an AI assistant — can grant.

**Two findings surfaced by writing the SSP/SAR carry more real weight than the rest:** no DoD PKI/CAC authentication (local username/password is real but not DoD-grade identity), and the still-unresolved OpenRouter LLM data-exposure decision first named in round 6's governance notes, now formalized as a specific SC/CA control gap with a specific POA&M line. Both are named as needing an organizational decision, not more solo engineering — consistent with this project's practice throughout of saying plainly what a gap actually requires rather than implying more code would close it.

### 4.9 Frontend rebuild: FastAPI + React, replacing Streamlit

Streamlit got the prototype to a working end-to-end demo quickly, which was the right call for the original timebox (Section 4.1). But its default chrome — sidebar radio nav, stock widgets, no design system — reads as "internal script with a UI bolted on," not as a tool anyone would mistake for a product. At the user's request, and after being offered a cheaper Streamlit-reskin alternative and explicitly choosing the larger rebuild, the presentation layer was replaced.

**What changed:** a new FastAPI backend (`api/`) and a React + TypeScript + Tailwind single-page app (`frontend/`), styled to enterprise-BI conventions drawn from Power BI, Tableau, and Looker (neutral canvas, white cards on that canvas, one accent blue used sparingly rather than per-series, dense KPI tile row, muted categorical chart palette, persistent left rail). `app/main.py`, `app/dashboard.py`, and `app/governance_panel.py` were deleted; `streamlit` and `plotly` left `requirements.txt`.

**What deliberately did not change:** the data generator, cleansing pipeline, DuckDB semantic layer, measure registry, and both NL interpreters. This was a presentation-layer swap, not a rewrite — every dashboard's SQL was carried over verbatim into the corresponding route handler, and `tests/test_questions.py` was re-run afterward to confirm the interpretation logic was untouched (same 21/25 result as before the rebuild).

**The one interface that had to change**, and why it's a better boundary: `app/nl_query.py::answer_question()` used to build a Plotly figure directly. It now returns a JSON-serializable `chart` spec — `{kind, x, y, color}` — naming which columns to plot and how. The NL layer no longer knows or cares what renders it, which is what made an entirely different frontend possible without touching interpretation logic at all.

**Auth moved from Streamlit's server-side session state to a signed JWT in an httpOnly cookie** (`api/deps.py`, `api/routers/auth.py`). `auth/auth.py` was refactored to be framework-agnostic — it now only does credential verification, role checks, and audit logging, with no knowledge of how a session is carried between requests. Role gating is enforced in two places on purpose: the SPA hides admin nav and redirects admin routes, and the API independently rejects non-admin callers with a 403 — verified directly with `curl`, since a client-side-only guard is a UI convenience, not access control (AC-3).

### 4.10 Performance optimization pass

Six changes, made after the rebuild at the user's request, each addressing something measured rather than assumed:

- **Persistent DuckDB connection** (`warehouse/semantic_layer.py`): every `query()` call previously opened and closed a fresh file-backed connection — several times per page load. Now one process-wide connection, guarded by a lock since FastAPI runs sync handlers in a threadpool. **This one had a real gotcha:** opened read-write, the persistent connection held an exclusive file lock for the server's entire lifetime, which broke `tests/test_questions.py` the moment it ran while the server was up. Caught it during verification, not by reasoning about it in advance. Fixed by opening read-only (`query()` only ever runs SELECTs; the sole writer is `build_warehouse()`, which uses its own short-lived connection before this one exists), which DuckDB permits multiple processes to hold concurrently.
- **Cached entity vocabulary** (`app/nl_query.py::_load_entity_lookup`): ran 4 SQL queries on *every* "Ask a question" request to rebuild a vocabulary that only changes when the warehouse is rebuilt. Now `lru_cache`d.
- **Cached governance reads** (`api/routers/governance.py`): the row-count reconciliation re-read 6 files from disk per page visit; the cleansing log likewise. Both now cached.
- **Gzip compression** (`api/main.py`): dashboard/drill-down/audit-log responses are JSON arrays of a few hundred rows.
- **LLM answer cache** (`api/routers/ask.py`): a 10-minute TTL cache keyed on normalized question text, so re-asking an identical question skips the OpenRouter call entirely — measured 1.8s → 0.019s on a cache hit. The audit log still records every request, cached or not; caching skips the recompute, never the "who asked what" trail.
- **Frontend code-splitting and table virtualization** (`frontend/src/App.tsx`, `frontend/src/components/VirtualizedTable.tsx`): routes are `React.lazy`-loaded, dropping the initial bundle from 840KB (248KB gzipped) to 279KB (88KB gzipped) with Leaflet and Recharts moved into on-demand chunks; Drill-down and Audit Log — the two tables that can actually grow — now render only visible rows.

### 4.11 Test coverage, CI, secret handling, and deployment posture

The rebuild in 4.9 left a real gap: `tests/test_questions.py` only ever exercised NL interpretation, so the entire API layer and frontend had no automated coverage at all — their only verification was the manual browser pass done at the time. Four things closed that.

**API tests (`tests/test_api.py`, 44 tests).** Run against the real FastAPI app, the real DuckDB warehouse, and the real seeded accounts rather than mocks, because the thing worth testing *is* the wiring — a suite built on mocked internals would stay green while auth, role checks, and the semantic layer came apart. The access-control tests carry the most weight: an analyst with a perfectly valid session must still get a 403 from every admin endpoint, which is the claim `rmf/SSP.md`'s AC-3 entry makes. Also covered: forged and expired tokens, a token signed with the wrong key, a hand-tampered payload with `role` escalated to `admin`, and the response-shape contracts the SPA reads (renaming a column in `measures.sql` without updating the frontend would otherwise render axes with no bars).

**Writing those tests immediately found a real bug**, which is the strongest argument for having written them. `api/routers/audit.py` used a bare `df.to_dict()`. A question the app doesn't understand logs `interpreted_by=None`, which round-trips through the CSV as a pandas `NaN`, which serializes as a bare `NaN` token — invalid JSON. So the first unrecognized question anyone asked would **permanently 500 the admin Audit Log page**: precisely the record that's supposed to be dependable, broken by the app's own honest "I don't understand" path. Fixed by routing through `api/utils.py::df_to_records` (the same helper the dashboard routes already used), and applied to the cleansing-log endpoint too, which had the identical latent pattern.

**Frontend tests (33 tests, Vitest + React Testing Library).** Concentrated where silent-wrong-output bugs live rather than spread thin for coverage's sake: `pivotForMultiLine` (the long→wide reshape that feeds every multi-series chart — including that a unit with no missions in a month stays `undefined` rather than becoming `0`, since "not recorded" and "zero" are different claims this codebase is deliberate about), CSV export escaping (unquoted commas silently shift columns), the client half of role gating, and the Ask page's caveat rendering. Two notes on the harness: jsdom reports every element as 0×0 and implements no scrolling, so `ResizeObserver`/`getBoundingClientRect`/`scrollTo` are stubbed in `src/test/setup.ts` — environment gaps, deliberately not "fixed" by weakening app code to suit the test runner.

**CI (`.github/workflows/ci.yml`).** Backend job runs pytest on a Python 3.9 + 3.11 matrix (3.9 is what this project is actually developed on; 3.11 catches modern-runtime breakage — testing one alone lets the other direction through), building the synthetic data and warehouse first exactly as `./run.sh` does. No `OPENROUTER_API_KEY` is set there on purpose: the API tests force the deterministic keyword path, and pointing CI at a rate-limited free model would make builds fail on quota rather than on regressions. Frontend job runs typecheck, lint, tests, and build. Verified before committing by running the full backend sequence in a clean copy of the repo with no generated artifacts — 44 tests passed against freshly generated data, confirming the tests aren't coupled to one particular local dataset.

**Secret handling.** `api/deps.py` previously fell back to a hardcoded dev `JWT_SECRET`. A known signing key sitting in a repository means anyone with the source can mint a valid admin session, so the fallback is now a random per-process secret with a startup warning. The only cost is that restarting the server invalidates existing sessions — a non-issue for a local demo, and fixed by setting `JWT_SECRET` explicitly. This also makes `rmf/SSP.md`'s CM-6 note true: no default credential ships in this codebase.

**Deployment posture.** Two additions, with honestly different levels of verification:
- **Static-serving mode (`./run.sh --prod`)** — builds the SPA and serves it from the same Uvicorn process as the API: one process, one port, no CORS, and a plainly first-party cookie. `api/main.py`'s catch-all returns `index.html` for client-side routes so a hard refresh or a pasted deep link works (the classic SPA deployment bug that never appears under a dev server), while unknown `/api/*` paths still return JSON 404s rather than a page of HTML. **Verified end-to-end**, including in the browser: deep-linking to `/governance` while signed out serves the shell, redirects to login, and lands back on the requested page.
- **Docker (`Dockerfile`, `docker-compose.yml`, `docker-entrypoint.sh`)** — multi-stage build (Node builds the SPA, the Node toolchain doesn't ship in the final image), non-root user (uid 10001), healthcheck against `/api/health` rather than the static shell, since the shell is a static file that would return 200 even with a broken warehouse. One design bug was caught by reading before any of this was run: the first draft mounted named volumes over `data/`, `auth/`, and `warehouse/`, which hold application code as well as generated files. A named volume seeds itself from the image once and then shadows that path, so a later rebuild would silently run stale code. Replaced with a single volume at a dedicated `/app/var`, plus a new `NAVYBI_AUDIT_LOG_PATH` override — the audit log is the one piece of state that genuinely can't be regenerated, whereas the dataset, warehouse, and demo accounts all rebuild deterministically.

  **Initially shipped unverified** (Docker wasn't installed on the build machine) and flagged as such, then verified once Colima was installed — Colima rather than Docker Desktop because Docker Desktop needs an admin password on first launch to install privileged helpers, while Colima runs the same Linux VM without one (and sidesteps Docker Desktop's licensing terms). Verified: the image builds first try, the entrypoint generates data → builds the warehouse → seeds accounts → starts Uvicorn, the container reports `healthy`, it runs as uid 10001 rather than root, `/app/var` is the only mount (code directories confirmed un-shadowed), auth and role gating behave identically to the host (analyst → 403 on governance, unauthenticated → 401), gzip still applies, and the audit log survives `docker compose restart` — including a row whose `interpreted_by` is null, which is the bug from earlier in this section, confirmed fixed inside the container too. Compose also picks up the local `.env` automatically, so the real LLM path works containerized (verified in the browser: an LLM-interpreted answer with the 🤖 badge and a correct chart).
