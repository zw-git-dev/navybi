### The important finding (round 1)

The two "wrong but confident" cases (#10, #12) are the risk that matters most, and it isn't unique to template matching — it's a general risk for *any* NL-to-query system, including a real LLM one: **a system that fails silently into a plausible-looking but wrong-scoped answer is more dangerous than one that says "I don't understand,"** because a user has no reason to doubt a chart that renders normally. The honest rejections (#9, #13, #15) are the *safe* failure mode; #10 and #12 are the *unsafe* one.

## Fix applied

Three changes to `app/nl_query.py`, in response to round 1:

1. **Equipment entity filtering** — `interpret_question()` now also matches equipment-type names (it previously only matched unit and mission-type names), so a question naming a specific piece of equipment actually filters to it. Fixes #14.
2. **Superlative-aware sorting** — "lowest/minimum/worst/least" now sorts ascending instead of always descending, so "which X has the lowest Y" surfaces the right end of the table instead of making the user read it off themselves. Fixes #5.
3. **Scope-mismatch caveats (the safety fix)** — `interpret_question()` now detects two specific unsupported-but-mentioned asks (a community name with no community-level measure; a trend/time-series request against a measure with no time dimension) and returns them as a `caveats` list. `app/main.py` renders each caveat as a prominent `st.error` block *above* the answer, not a footnote — directly addresses #10 and #12 by turning a silent wrong-scope answer into a loud, explicit "this part of your question was NOT answered."

## Round 3: closing #7 and #11

Two more changes to `app/nl_query.py`:

1. **"Last N months" windowing** — the trend intent now extracts an explicit number from phrasing like "last 6 months" / "past 3 months" and filters the result to the last N months *actually present in the data* (not N calendar months back from wall-clock "today" — there is no "today" in a historical reporting dataset). A vague relative-time phrase with no number ("recent months," "lately") now produces an explicit caveat instead of silently showing everything. Fixes #7.
2. **Order-independent phrase matching** — the completion intent now also matches when "objective" and "met" both appear anywhere in the question, not just as the literal substring "objective met." Fixes #11's specific phrasing ("met their objective").

### A real bug found during live verification of fix #1

Testing "Show me mission trends over **the last 3 months**" in the running app (not just the offline test harness) surfaced an actual regression: the entity-matching fallback logic — meant to catch informal unit references like "Sqn 7" via a unit name's last word — matched the bare digit "3" in "last 3 months" against unit "Carrier Air Wing **3**", silently scoping the answer to one unit that was never mentioned. This is exactly the kind of confident-but-wrong-scope failure the round-1/round-2 work was supposed to eliminate, and it slipped in from a *different* code path than the one that was fixed. The fallback now requires at least one other, non-trivial word from the unit's name to also appear in the question (e.g. "carrier" or "wing"), not just the trailing number, closing the hole without losing the informal-reference case it existed for.

**Why this matters beyond the specific fix:** the round-1 test log argued that explainability (showing the SQL/definition on every answer) was the only reason the original two silent-wrong-scope cases were catchable. This bug is direct evidence for that argument holding up in practice — it was caught by actually looking at a rendered answer in the browser, not by the automated test list, because the test list never happened to combine "a number in the question" with "a unit name ending in that same number." **Any scope-safety mechanism needs to be re-verified against live use, not just a fixed test set, since new code paths can reintroduce the exact failure mode a previous fix closed.**

## Round 4: adding a second data source surfaced two more real bugs

A training/certification records source (JSON, joined through `personnel` to reach `units` — the first two-hop relationship in the semantic layer) was added, with a new `training_currency` intent in `app/nl_query.py`. Four new questions (#16-19) were added to the test set to exercise it. Testing them immediately found two real bugs, neither hypothetical:

- **#18 "Show me training currency trends by month" — the dangerous failure mode recurred, in a new form.** `INTENTS` is matched first-match-wins by list order, and the generic "trend" intent (keywords like "trend," "by month") was checked *before* the new `training_currency` intent. A question that was unambiguously about training got matched to the mission-count trend intent instead, silently returning a completely unrelated chart (mission counts, not training data) with **no caveat at all** — worse than round 1's cases, because those at least stayed in the right topic area. **Fix:** restructured matching so domain-specific intents (completion, readiness, duration, training) are always checked before the generic "trend" intent; "trend" only wins when no domain-specific keyword matched. Now this question correctly resolves to the `training_currency` intent, which has no month dimension, and the existing round-2 caveat mechanism catches it and reports the mismatch explicitly — the fix didn't just patch this one phrase, it fixed the general ordering flaw that would have recurred with the *next* new domain added, too.
- **#19 "Which units have the most expired certifications?" — a real sort-direction bug.** "Most" is a generic descending-sort keyword, but "most expired" is the low end of `currency_rate_pct` (a positive-framed measure), not the high end — the generic superlative logic returned units with the *best* currency first, the opposite of what was asked. **Fix:** added a narrow, measure-specific override — "expired"/"lapsed"/"overdue" force ascending sort on the training-currency measure regardless of what superlative word is also present. Verified against the actual rendered chart (not just the returned dataframe, which isn't sorted) that the lowest-currency unit now appears first.

- Fully correct: 13/19 (68%) — the original 10/15 plus #16, #17, #18 (now safely caveated, counted separately below), #19.
- Correctly rejected: 4/19 (21%) — unchanged (#9, #13, #15).
- Safely caveated: 3/19 (16%) — #10, #12 unchanged, plus #18 (new).

**The pattern holding across all four rounds:** every round that added real surface area (a new question, a new data source) found at least one genuine bug, and in three of four rounds that bug was the same *shape* — a confident, normal-looking answer that was actually wrong or off-topic. This isn't evidence the mechanism is broken; it's evidence that scope-safety is a property of the *whole system as it grows*, not a box that gets checked once. The concrete, actionable version of that lesson: **any time a new intent, data source, or measure is added to this conversational layer, the full test set needs to be re-run and the result manually spot-checked in the live app, not just assumed to still hold.**

## Round 5: a third data source, plus adversarial probing beyond the fixed question set

A maintenance/discrepancy events source was added — the first ingested from an actual SQL database (SQLite) rather than a flat file — with a new `maintenance` intent covering two genuinely different measures (downtime by equipment, resolution rate by unit). Six questions (#20-25) were added for it, all of which passed immediately. Rather than stop there, this round also ran **adversarial probes deliberately designed to break the matcher**, not just realistic questions — the same instinct that caught the round-3 and round-4 regressions, applied proactively instead of waiting for an accident. It found two more real bugs, one of them serious:

- **A wrong-domain answer via accidental substring collision, not entity-name overlap this time.** The probe "The unit has already completed most of its missions this quarter" — a question about nothing in this system's scope — was answered with an **equipment readiness chart**. Cause: the readiness intent's keyword `"ready"` was matched via plain substring, and `"ready"` is literally contained inside `"already"`. This is a different flavor of the same failure family as round 4's mission-type collision (#24/#25 in this round: "ASW Training" colliding with the training-currency intent), but the mechanism is more general and more dangerous — it isn't limited to this system's own vocabulary colliding with itself, it's *any* single-word keyword colliding with *any* English word that happens to contain it. **Fix:** every keyword check across the file now goes through a shared `_kw_in()` helper that requires word boundaries for single-word keywords (multi-word phrases stay substring-matched, since they're long enough not to false-positive in practice). Multi-word phrases like "how long" or "objective met" are unaffected.
- **The fix immediately caused its own regression, caught before being called done.** Applying strict word boundaries broke question #7 ("mission **trends**") — the singular keyword `"trend"` no longer substring-matched the plural `"trends"` once boundaries were enforced, since English pluralization doesn't insert a word boundary before the "s". Re-running the full 25-question set (not just the two adversarial probes) immediately surfaced this. **Fix:** `_kw_in()` now allows an optional trailing "s" for single-word keywords. This is the round's clearest demonstration of the round-4 lesson: **a fix for one bug needs the same full-suite-plus-live-check treatment as the original bug**, because it can introduce a new one in the process of closing the old one.
- **A second sort-direction bug, same shape as round 4's "most expired."** "Which units have the most unresolved discrepancies?" defaulted to descending sort on `resolution_rate_pct` (via the generic "most" keyword), showing the *best*-performing units first for a question asking about the *worst*. Same root cause as training currency's "most expired," different measure. **Fix:** the same override pattern extended to maintenance's resolution dimension for "unresolved"/"not resolved"/"outstanding"/"open discrepancies." Also required adding "unresolved"/"outstanding" as explicit first-class keywords rather than relying on "resolved" substring-matching them, since the word-boundary fix above (correctly) stopped treating "unresolved" as containing the word "resolved."

- Fully correct: 15/25 (60%) — the original 13/19 plus 4 of the 6 new maintenance questions (#20, #21, #22, #23), minus the temporary #7 regression (caught and fixed before this count was taken).
- Correctly rejected: 6/25 (24%) — #9, #13, #15 unchanged, plus #24 and #25 (the round-4 mission-type collision questions, still correctly rejected after this round's changes — re-verified, not assumed).
- Safely caveated: 3/25 (12%) — #10, #12, #18 unchanged.
- Wrong but confident: 0/25 (0%) — re-verified after three rounds of fixes within this single round, including the fix that broke and then re-fixed #7.

What's interesting is that **this round found bugs by going looking for them** — the adversarial probes weren't part of the "realistic question" set and wouldn't have been caught by simply waiting for round 6 to stumble into them. That's a deliberate escalation from rounds 1-4 (which found bugs via realistic questions or live use) and arguably should have started earlier.

## Round 6: the LLM swap actually happens

Rounds 1-5 all tested and hardened the keyword-matching stand-in, while `app/nl_query.py`'s docstring kept pointing at a real LLM as the eventual answer to the keyword matcher's ceiling. Round 6 is that swap actually happening: `app/llm_interpret.py` calls `nvidia/nemotron-3-ultra-550b-a55b:free` via OpenRouter, using tool-calling to force structured output in the exact same `(matched_intent, dimension, entity_filter)` shape the keyword matcher produces, so every downstream mechanism built in rounds 1-5 (entity-to-dimension resolution, sort-order overrides, the scope-mismatch caveat system) applies unchanged regardless of which interpreter answered. The keyword matcher stays as the fallback for when the LLM isn't configured or a call fails.

This was tested against real API calls, not mocked — and, consistent with every prior round, testing found real, previously-impossible bugs the moment new behavior became possible:

- **A crash, not just a wrong answer — the most severe failure mode found in any round.** Asked "How many ASW Training missions were flown?", the LLM correctly classified the question as the `trend` (mission-count) intent, but also attached `entity_type="mission_type", entity_value="ASW Training"` — a syntactically valid entity from the known vocabulary. The `trend` view has no `mission_type` column at all. The result was an unhandled `DuckDB BinderException`, a full crash, not a wrong-but-rendered chart. This was possible with the keyword matcher too (nothing stopped it from producing the same combination) but never happened by accident in five rounds — the LLM's more deliberate entity-attachment made it a near-certainty rather than a coincidence. **Fix:** every intent now declares `valid_entity_columns`, checked centrally in `interpret_question()` before any entity_filter reaches SQL; a mismatch is dropped and reported as an explicit caveat ("mentioned a specific mission type, but this measure can't filter by that") instead of crashing or being silently ignored. This is a new tier of safeguard beyond the wrong-scope caveats from rounds 1-2 — it's the difference between "confidently wrong" and "confidently broken."
- **The LLM confidently rejected a question the keyword matcher could answer, because the prompt didn't explain what the measures meant.** "Which units have the most unresolved discrepancies?" initially got `no_match` from the model — not a technical failure, an actual "this doesn't match anything" determination — because the tool schema gave it only intent IDs and dimension names (e.g. `maintenance (dimensions: downtime, resolution)`) with no explanation of what "maintenance" actually covers. **Fix:** added an `llm_description` field to every intent (e.g. maintenance: "whether logged maintenance discrepancies/issues have been resolved or are still outstanding/unresolved") and threaded it into the prompt. Re-tested: correctly resolved afterward, with the ascending-sort override still applying via the shared downstream logic.
- **A design tradeoff, observed rather than fixed: the LLM's authoritative "no" isn't always the most helpful answer available.** "readiness trend by month" — a question the keyword matcher answers today with a real chart plus a caveat explaining readiness has no time dimension — instead got a clean `no_match` from the LLM after a genuine ~41-second reasoning pass. Per this round's design (an LLM `no_match` is treated as authoritative and does NOT fall back to the keyword matcher, since the model actually reasoned about it), the user got a bare "I don't understand" instead of the more informative caveated answer the keyword matcher would have given. This is not a bug in the sense of being wrong — an honest rejection is still the safe failure mode established since round 1 — but it is a real regression in *helpfulness* worth naming plainly: **a well-reasoned "no" from a smarter interpreter can still be a worse user experience than a well-caveated "sort of" from a dumber one.** No fix applied; flagged as an open design question below.
- **Real-world rate limiting on the free model, and the fallback design worked exactly as intended.** Partway through a 25-question run, calls started failing near-instantly (~0.1s, vs. multi-second real responses) — the free tier's rate limit, not a bug. Every one of those questions fell through to the keyword matcher automatically and either answered correctly or failed the same way it always has (no worse than before the LLM was added). This is the "fall back to the template matcher" design decision from earlier in the conversation working as designed, confirmed under real conditions rather than only in a unit test.

### Round 6 follow-up: the open design question, resolved with user input

The question above was a genuine product judgment call, not a bug with one correct fix — so it was resolved by asking, not by unilateral decision. Three questions, three decisions:

1. **Should an LLM `no_match` still trigger a keyword-matcher check?** Yes. `interpret_question()` no longer returns immediately on `no_match` — it runs `_interpret_via_keywords()` as a second opinion, same as it already did for technical failures.
2. **How much should that second opinion be trusted?** Only when it comes back WITH a caveat. A caveat means the keyword matcher is itself flagging a limitation ("no time dimension for this measure"), which is a fundamentally different, lower-risk situation than a *clean* keyword match contradicting an LLM rejection — a clean match in that situation is more likely the keyword matcher's own false positive (the exact failure mode five rounds of hardening were about) than a genuine LLM miss, so it's discarded and the LLM's "no" stands.
3. **How should the surfaced answer be labeled?** As the primary answer, not a buried suggestion, tagged distinctly: `interpreted_by = "keyword_after_llm_no_match"`, rendered in the UI as "🔤 keyword/entity matcher (the LLM found no match, but the keyword matcher found this partial answer)" — so the user can see the two interpreters actually disagreed, not just get an unexplained answer.

**Verified deterministically** (not just by hoping to reproduce the exact live "no_match" again, since the free model's response isn't reproducible on demand): mocked `interpret_via_llm` to return `no_match` and confirmed all three branches behave as designed —
- "readiness trend by month" → keyword matcher's caveated answer now surfaces (`interpreted_by = "keyword_after_llm_no_match"`, caveat present) — the case that motivated this whole fix.
- "What is the mission completion rate by unit?" (LLM incorrectly says no_match, keyword matcher gets a *clean* match) → discarded, `understood = False` — confirming the trust gate actually holds and doesn't just pass through anything the keyword matcher finds.
- A genuinely out-of-scope question → both interpreters find nothing, honest rejection, unchanged.

Also re-ran the full 25-question suite with the LLM path disabled to confirm this change doesn't touch the keyword-only baseline at all — identical results to round 5, question for question.

## Round 7: swapping the LLM model (Nemotron → Gemma)

Nemotron (`nvidia/nemotron-3-ultra-550b-a55b:free`) was heavily rate-limited on its free tier and slow (a reasoning model, sometimes 20-40+ seconds per call). At the user's request, swapped `OPENROUTER_MODEL` to `google/gemma-4-31b-it:free` — verified to exist and support tool-calling via OpenRouter's public model list before switching, same diligence as round 6's original model choice.

**The switch was a large, clear improvement on the axes it was made for:** average LLM latency dropped from Nemotron's multi-second-to-40-second range to ~1.8s, and a full 25-question run hit the free tier's rate limit far later (questions ~19-23 fell back, vs. Nemotron's ~21-25) — both expected, since Gemma isn't a reasoning-by-default model. The keyword-matcher fallback engaged automatically for the rate-limited questions and answered exactly as it always has, same as round 6's fallback validation.

**It also introduced two new, real, model-specific bugs** — a reminder that swapping *which* LLM answers is exactly as much a "new surface area" as adding a data source or a new intent, and needs the same re-verification, not an assumption that one model's fixes carry over to another's:

- **A confident wrong-domain answer with NO caveat — the dangerous failure mode round 1-5 existed to eliminate, reopened by a different model's classification bias.** "readiness trend by month" and "training currency trends by month" were both answered with the unrelated mission-count-by-month chart, `caveats: []`. Nemotron never did this; Gemma appears biased toward the generic "trend" intent whenever a question mentions time, more strongly than Nemotron was. Round 6's entity-schema validation didn't catch it because the query was valid SQL against a real view — the LLM had simply picked the wrong intent outright, with no invalid entity to flag. **Fix:** added a cross-check, run regardless of which interpreter is active, specific to the "trend" intent: whenever ANY interpreter lands on "trend," re-run the keyword matcher's own domain-priority logic (which already exists specifically to prefer domain-specific intents over generic "trend" — see round 4) as a sanity check. If keyword matching would pick a different, non-trend intent, that intent wins, and the existing time_trend-mismatch caveat fires automatically for it. This makes an existing safeguard, originally built for one interpreter, protect both — without needing model-specific tuning.
- **A ranking question got a technically-valid but practically-useless chart, with no caveat.** "Which unit has the most missions overall?" — a question requiring a single ranked total — was answered with the trend view's raw per-month line chart (correct domain, wrong *shape* of answer; a line chart can't itself show "which one is highest overall," only data a person could eyeball to guess at it). Nemotron had rejected this question outright (`no_match`); Gemma answered confidently instead. This is a genuinely new caveat category, not a repeat of an existing one — every prior caveat was about the wrong *measure* or an unsupported *filter*; this is about the right measure with a chart type that structurally can't answer what was asked. **Fix:** a new caveat: when the "trend" intent is selected with no entity filter (i.e., comparing across units, not looking at one) and the question contains ranking language ("most," "highest," etc.), a caveat now says so explicitly rather than presenting the chart as if it settled the question.

### Round 7 results

Re-ran the full 25-question suite after both fixes: identical correct/caveated/rejected outcomes to the established baseline, with the two new cases now correctly caveated instead of silently wrong. No regressions found on the previously-passing bar-chart-based superlative questions (e.g. "which equipment type has the lowest average readiness" is unaffected — that measure has real ranking support, so the new caveat's `matched_intent["id"] == "trend"` condition correctly excludes it).

**The pattern holds for a sixth and seventh time, now across TWO different axes of change (new domain surface AND a different model):** any new dimension of change to this system — a data source, an intent, a new interpreter, or now a different model behind the same interpreter — needs the same full-suite-plus-live-verification treatment, not a one-time pass. A model swap made purely for speed/cost reasons is not risk-free just because "it's still an LLM behind the same interface."

## Remaining known gap (accepted, not fixed)

**Keyword matching still has an open-ended false-negative surface.** Round 3 closed the *specific* phrasing gap found in testing (#11), but the underlying limitation — a fixed keyword list will always miss some real phrasing of a real intent — is not fixable by patching individual phrases one at a time; it's the fundamental ceiling of this technique. This remains the strongest concrete argument in this repo for the LLM swap described in `app/nl_query.py`'s docstring: a real language model would generalize across phrasing variations by construction, rather than needing each variation discovered and special-cased.

The caveat mechanism itself also remains a targeted patch (a small, growing list of specific unsupported-dimension and wrong-direction patterns), not a general solution. A real LLM-based interpreter would still need an equivalent scope-verification step — e.g. asking the model to self-report which parts of a question it could and couldn't honor — not just better language understanding. That general requirement, not any of these specific patches, is the thing worth carrying into any production version.

**Word-boundary matching (round 5) closes accidental-substring collisions ("ready"/"already") but not deliberate ones.** The `_kw_in()` fix handles the generic case of a keyword coincidentally appearing inside an unrelated English word. It does NOT and cannot handle a keyword that's a genuine, meaningful substring of a *different domain's real vocabulary* — that's what the round-4 mission-type collision (`training`/`qualification` vs. `ASW Training`/`Deck Landing Qualification`) actually was, and it needed its own bespoke veto logic, not a generic string-matching fix. Every new intent added to this file should be checked by hand against the existing entity vocabulary (unit names, mission types, equipment types, certifications) for exactly this kind of overlap — it is not something `_kw_in()` or any other generic mechanism catches automatically.
