# Governance Notes: DoW Ethical Principles Applied to This Prototype

This maps the Department of War's five AI ethical principles (Responsible, Equitable, Traceable, Reliable, Governable) against what was actually built in this 24-hour prototype — what's genuinely true now, and what remains real work for anything beyond a demo. This is a self-assessment of a proof-of-concept, not a compliance certification, and it is not a substitute for an actual RMF package or ATO process.

## Responsible

**True now:** A human remains the decision-maker at every step — the tool surfaces data and computed measures, it does not issue recommendations or take autonomous action. Every automated cleansing decision (dedup, null handling, outlier flagging) is logged with a plain-language reason (`data/clean/cleansing_log.json`, surfaced in the app's governance panel) rather than applied silently.

**Still needed:** A named responsible owner/office for the tool's outputs, a documented process for what happens when a user acts on a wrong or misleading answer (see the Reliable section below — this is a real, demonstrated failure mode, not hypothetical), and use-case boundaries (what decisions this tool is and isn't appropriate to inform).

## Equitable

**True now:** The measure definitions (completion rate, readiness, duration) are applied identically across every unit and mission type — there's no unit-specific or role-specific weighting built in that would favor one group's data over another's.

**Still needed:** This is unevaluated at real scale, since the dataset is synthetic and small. A real deployment would need to check whether data completeness itself varies systematically by unit (e.g., if some units report more diligently than others, "worse" metrics for a unit may reflect better reporting discipline, not worse performance) — a bias risk to test for once real reporting data is involved, not something that can be verified against fabricated data.

## Traceable

**True now:** This is the principle the prototype invests in most. Every dashboard chart and every conversational answer traces to an exact, visible SQL statement against a named semantic-layer view, with a plain-language measure definition shown alongside it, and a drill-down page for manual row-level verification. The [conversational layer test log](QUESTION_TEST_LOG.md) documents exactly where the current interpretation step succeeds, fails safely, and — more importantly — fails silently into a wrong-but-confident answer (see that log's "important finding").

**True now, as of the multi-user auth work:** the prototype now has real user accounts (`auth/`, two roles) and audit logging of who asked what and when — every conversational query is recorded with username, role, timestamp, question text, which interpreter answered it, and whether it was understood, visible to admins via the in-app Audit Log page. This directly closes what was previously the top item in this section's gap list.

**Still needed:** A version history for the semantic layer's measure definitions as they inevitably get refined, and the audit log itself still needs protection (access control, tamper-evidence, retention policy) beyond ordinary filesystem permissions — see [rmf/SSP.md](rmf/SSP.md)'s AU-9/AU-11 control entries and [rmf/POAM.md](rmf/POAM.md) item #3.

## Reliable

**True now:** The cleansing pipeline handles real data-quality problems (duplicates, nulls, impossible values, inconsistent formats) explicitly and observably rather than silently. The question test log gives a real, measured accuracy figure (6/15 fully correct) rather than an assumed one, including the two cases where the system answered confidently but incorrectly.

**Still needed:** The measured accuracy rate (60% fully correct as of the latest keyword-matcher-only test round on a harder, adversarially-expanded question set, up from 40% on the original set across five rounds of targeted fixes — see QUESTION_TEST_LOG.md) is a known limitation of the keyword-matching fallback, not a claim about what the LLM path achieves. A real LLM (OpenRouter) was wired in for round 6 (`nvidia/nemotron-3-ultra-550b-a55b:free`) and testing it against the live API immediately found a new, more severe failure class than anything the keyword matcher produced: an actual unhandled crash (a `DuckDB BinderException`) from the model attaching a valid-vocabulary entity to a measure whose view had no matching column — fixed with a hard schema-validation check run centrally before any entity reaches SQL, regardless of which interpreter produced it. Round 7 swapped the model to `google/gemma-4-31b-it:free` for speed/rate-limiting reasons, and testing found the swap itself reopened the round-1-through-5 "confident wrong-domain answer, no caveat" failure mode via a different model's own classification bias — fixed with a model-agnostic cross-check rather than a model-specific patch, precisely so the *next* model swap doesn't reopen the same hole again. The scope-mismatch caveat mechanism from round 1 has now been independently re-confirmed across all seven rounds, each time by catching a *new* instance of the same failure shape introduced by unrelated changes. The lesson holds up across seven independent tests now, across two different axes of change (new domain surface area, and a different model behind the same interpreter): scope-safety isn't a one-time patch, it's a property that has to be re-checked against real use every time the interpretation logic OR the model behind it changes — a more capable or faster interpreter does not retire this requirement, it just changes what breaks.

## Governable

**True now:** The NL query layer is architecturally isolated (`interpret_question()`) specifically so its behavior can be constrained, audited, or replaced without touching the data pipeline or semantic layer — a governance lever, not just a code-cleanliness choice. That isolation is what made both the round-6 LLM integration and the round-7 model swap (`nvidia/nemotron-3-ultra-550b-a55b:free` → `google/gemma-4-31b-it:free`, a one-line config change) possible without touching the dashboard, the semantic layer, or any of the safety mechanisms already built — though round 7 confirmed that a config-level model swap is not a config-level *risk*, since it reopened a real failure mode that needed its own fix.

**New consideration introduced by round 6, flagged explicitly rather than glossed over:** this is the first point in the prototype where data leaves the local environment. Every LLM call sends the user's question text plus the full known entity vocabulary (all unit names, mission types, equipment types, certifications) to a third-party API (OpenRouter, and whichever upstream provider actually serves the model) over the network. In this prototype that's synthetic, fabricated data, so the exposure is harmless — but the architecture itself would send the same categories of real organizational data (unit names, mission types, etc.) to an external commercial API if pointed at real data, with no data-handling agreement, no on-prem/air-gapped option, and no control over upstream logging or retention. **This is exactly the "security posture" and "LLM hosting" decision flagged as still-open back in the original 24-hour PLAN.md, now made concrete rather than hypothetical.** Any use of this LLM path beyond a synthetic-data demo requires that decision to actually be made — e.g. an on-prem/self-hosted model, a FedRAMP-authorized hosting arrangement, or an explicit acceptance of the data-exposure risk by whoever owns that decision — not assumed away by "well, it's just a chat API call."

**True now, as of the RMF/auth work:** a real (if minimal) authentication and role-based access system exists (`auth/`) — the prototype is no longer a single-user demo with no access control at all. A full RMF documentation package now exists in [rmf/](rmf/): a system categorization (both as-built Low and target Moderate/CUI, per [rmf/SYSTEM_CATEGORIZATION.md](rmf/SYSTEM_CATEGORIZATION.md)), a System Security Plan with control-by-control status grounded in actual code ([rmf/SSP.md](rmf/SSP.md)), a Security Assessment Plan and a preliminary self-assessment report ([rmf/SAP.md](rmf/SAP.md), [rmf/SAR.md](rmf/SAR.md)), and a POA&M with a named path to an actual ATO decision ([rmf/POAM.md](rmf/POAM.md)).

**Still needed, named plainly rather than implied as done:** this is a developer-authored self-assessment, not an independent security control assessment, and no ATO has been requested or granted — an ATO is a risk-acceptance decision by a designated Authorizing Official, not something this package can grant itself (see `rmf/POAM.md`'s "Path to an actual Authority to Operate" section for exactly what that requires). The two most consequential concrete gaps are unchanged: real identity management (DoD PKI/CAC, not local username/password accounts) and the LLM hosting/data-exposure decision named directly above — both are organizational decisions, not more application code.

---

**Bottom line:** this prototype demonstrates the *shape* of a system that could satisfy these principles — explainability and traceability especially, and now, real (if minimal) access control and a real starting RMF package — but satisfying them for real still requires real data, real independent assessment, and an actual Authorizing Official's decision, none of which a solo build can substitute for or grant itself.
